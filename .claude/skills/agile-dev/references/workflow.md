# 五角色协作工作流

## 标准工作流程

```
需求分析 (产品经理)
    ↓
架构设计 (架构设计师)
    ↓
开发规划 (开发规划师)
    ↓
代码实现 (开发工程师)
    ↓
测试验证 (QA工程师) ← 必须执行，不可跳过
    ↓
验收发布 (产品经理)
```

### 关键质量门禁

**质量门禁1: 开发工程师 → QA_Engineer**
- 开发工程师必须确保代码通过单元测试和回归测试
- 开发工程师在 IMPLEMENT_PLAN.md 中标记 Story 为"待QA测试"
- **QA_Engineer 必须执行自动化测试**（Web 应用使用 webapp-testing skill）
- P0 级别 Bug 必须全部修复才能进入下一阶段
- QA 测试不可跳过，不可仅依赖手动测试或用户测试

**质量门禁2: QA_Engineer → 产品经理**
- 提供 QA_TEST_PLAN.md 测试报告
- 列出所有发现的 Bug 和修复状态
- 给出发布建议（可以发布/不能发布/有条件发布）
- 只有测试通过后才能进入用户验收阶段

## 文档组织结构

```
docs/feature/<feature>/
├── REQUIREMENTS.md      # 产品需求文档 (产品经理)
├── ARCHITECTURE.md      # 技术架构设计 (架构设计师)
├── IMPLEMENT_PLAN.md    # 开发实施计划 (开发规划师)
└── QA_TEST_PLAN.md      # QA测试计划 (QA工程师)
```

## 协作原则

### 1. 文档先行
- 所有关键决策都记录在文档中
- 文档是角色间协作的主要媒介
- 保持文档的及时更新

### 2. 明确交接
- 每个阶段完成后明确交付物
- 接收方确认理解后再开始工作
- 保持沟通渠道畅通

### 3. 质量门禁
- 每个阶段都有明确的完成标准
- 不达标不进入下一阶段
- 问题及时反馈和解决
- **QA_Engineer 测试是必需阶段，不可跳过**
- **Web 应用必须使用自动化测试工具（webapp-testing skill）**

### 4. 灵活调整
- 保持计划的灵活性
- 根据实际情况合理调整
- 变更需要沟通确认

## 常见协作场景

### 场景1：新功能开发
```
产品经理 → 需求分析
  ↓
架构设计师 → 技术架构
  ↓
开发规划师 → 实施计划
  ↓
开发工程师 → 代码实现
  ↓
开发工程师 → 标记 Story 为"待QA测试"（必需）
  ↓
QA工程师 → 执行自动化 E2E 测试（必需，使用 webapp-testing skill）
  ↓
  ├─ 测试通过 → 继续下一步
  └─ 测试失败 → 返回开发工程师修复，然后重新测试
  ↓
QA工程师 → 生成待验证文档 to_be_verify.md
  ↓
QA工程师 → 告知用户验证方法（不阻塞）
  ↓
用户 → 自行验证（随时进行）
  ↓
开发工程师 → 开始下一个 Story/Epic 时检查 to_be_verify.md
  ↓
  ├─ 文档不存在 → 直接开始开发 ✅
  └─ 文档存在 → 询问用户验证结果
      ↓
      ├─ 验证通过 → 删除文档 → 提交代码到 GitHub → 开始开发 ✅
      └─ 发现问题 → 记录问题 → 安排修复 ⚠️
  ↓
产品经理 → 验收发布
```

### 场景2：Bug修复
```
QA工程师 → 提交bug报告
  ↓
开发工程师 → 分析修复
  ↓
QA工程师 → 回归测试
  ↓
产品经理 → 确认修复
```

### 场景3：技术重构
```
架构设计师 → 重构方案
  ↓
开发规划师 → 拆分任务
  ↓
开发工程师 → 执行重构
  ↓
QA工程师 → 回归测试
  ↓
产品经理 → 验收确认
```

## 角色间关键协作点

| 协作点 | 角色1 → 角色2 | 关键动作 |
|--------|--------------|----------|
| 需求澄清 | 产品经理 → 架构设计师 | 讨论技术可行性 |
| 需求确认 | 产品经理 → 开发规划师 | 确认用户故事 |
| 技术约束 | 架构设计师 → 开发规划师 | 传递架构要求 |
| 验收标准 | 开发规划师 → 开发工程师 | 明确交付标准 |
| 功能确认 | 开发工程师 → 产品经理 | 验证功能实现 |
| Bug反馈 | QA工程师 → 开发工程师 | 报告和跟进bug |
| 质量评估 | QA工程师 → 产品经理 | 提供测试报告 |
| 发布决策 | 产品经理 → 全体 | 确认发布时机 |
| Epic待验证文档生成 | QA工程师 → 用户 | 生成 to_be_verify.md 并告知验证方法 |
| 用户验证检查 | 开发工程师 → 用户 | 开发前检查 to_be_verify.md 并确认验证结果 |
| 验证通过提交 | 开发工程师 → Git | 验证通过后删除文档并提交代码 |
