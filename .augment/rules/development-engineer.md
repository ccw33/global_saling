## 测试规范

### 本项目测试文件组织（Python + pytest）

**目录结构**：
```
tests/
├── unit/            # 单元测试（快速、独立、Mock外部依赖）
├── integration/     # 集成测试（组件交互、可能用真实DB）
├── e2e/             # 端到端测试（完整流程、真实环境）
└── fixtures/        # 共享测试工具和数据

local_langgraph/
├── nodes/rewrite/test_*.py              # 模块内测试
└── context_engineering/tests/test_*.py  # 模块内测试
```

**命名规范**：
- 文件：`test_*.py`
- 函数：`test_*`（清晰描述测试场景）
- 类：`Test*`


**项目特定习惯**：
- ✅ **优先使用真实环境**：真实 LLM、真实数据库（配置文件中的 QA 环境）
- ✅ **详细日志输出**：打印测试步骤和结果，方便调试
- ✅ **异步测试**：使用 `@pytest.mark.asyncio` 装饰器
- ⚠️ **少用 Mock**：除非单元测试需要隔离，否则用真实服务

### 新功能开发测试流程（必须严格执行）

#### 步骤1：编写新功能测试
- 为新功能编写测试文件，放在项目约定的位置
- 测试应覆盖主要功能路径和边界情况
- 测试命名清晰，描述测试场景

#### 步骤2：运行新功能测试
- 运行新编写的测试，确保通过
- 使用项目的测试命令（查看 README、Makefile、package.json 等）
- 记录测试结果

#### 步骤3：运行全量回归测试（关键步骤）
**在新功能测试通过后，必须运行所有历史测试，检查对旧功能的影响**

**本项目测试命令**：
```bash
# 运行所有测试
pytest

# 运行特定类型
pytest tests/unit/           # 单元测试
pytest tests/integration/    # 集成测试
pytest tests/e2e/            # E2E测试

# 运行模块内测试
pytest local_langgraph/nodes/rewrite/
pytest local_langgraph/context_engineering/

# 生成覆盖率报告
pytest --cov=local_langgraph --cov-report=html

# 使用测试脚本
./scripts/test/run_tests.sh all
./scripts/test/run_tests.sh coverage
```

**注意事项**：
- 记录所有测试结果
- 观察是否有测试失败或警告
- 覆盖率报告在 `htmlcov/` 目录

#### 步骤4：处理测试失败
**如果回归测试发现问题，必须先告知用户再修复**

1. **记录问题**：
   - 哪些测试失败了
   - 失败的具体错误信息
   - 分析失败原因（是新功能引入的问题还是测试需要更新）

2. **提供解决方案**：
   - 方案A：修改新功能代码以兼容旧功能
   - 方案B：更新旧测试以适应新的行为（需说明为什么旧行为需要改变）
   - 方案C：其他解决方案

3. **等待用户确认**：
   - 向用户说明问题和解决方案
   - 等待用户选择方案后再执行修复

4. **执行修复**：
   - 按用户确认的方案修复问题
   - 再次运行全量测试，确保所有测试通过

#### 步骤5：完成确认
- 所有测试（新功能 + 回归测试）都通过
- 提供手动验证的方法，让用户验证后确认
- 代码符合项目规范
- 更新项目文档或日志（如有要求）

### 测试质量标准
- **覆盖率**：新功能的主要路径必须有测试覆盖
- **独立性**：测试之间相互独立，不依赖执行顺序
- **确定性**：测试结果可重复，不受外部环境影响
- **清晰性**：测试失败时能快速定位问题

## 核心职责

### 开发实现原则
- **小步快跑**——每次改动都要能编译、能通过测试
- **向现有代码学习**——先研究、再规划、最后动手
- **务实优先**——根据项目现实灵活调整，不教条
- **清晰意图**——写得"无聊"且一目了然，拒绝炫技
- **简单设计**——每个函数/类只承担一项职责，避免过早抽象

### 开发实现流程
1. **理解**——研究代码库里的既有模式和实现方式
2. **设计**——基于现有模式设计最简单的实现方案
3. **编码**——编写清晰、可读的代码实现
4. **测试**——编写测试验证功能正确性
5. **重构**——在测试通过的前提下优化代码结构
6. **提交**——确保代码质量和提交信息清晰

### 代码质量标准
- **编译通过**——每次提交必须能正常编译
- **测试通过**——所有现有测试必须继续通过
- **新功能测试**——新功能必须附带相应测试
- **格式规范**——符合项目的格式和lint规则
- **提交检查**——运行格式化/lint工具，自我review改动

### 错误处理开发
- **快速失败**——代码出现问题时立即报错
- **描述性错误**——提供清晰的错误信息和调试上下文
- **异常处理**——在合适层级处理异常，不默默吞掉异常
- **防御编程**——对输入进行验证，预防错误发生

### 测试驱动开发
- **测试先行**——先写测试，再实现功能（红灯→绿灯）
- **行为测试**——测试行为，不测试实现细节
- **单一断言**——尽可能每个测试只有一个断言
- **确定性测试**——测试必须具有确定性和可重复性

### 代码实现规范
- **命名清晰**——变量、函数命名准确描述其用途
- **函数简洁**——每个函数只做一件事，保持简短
- **注释适度**——代码自解释为主，必要处添加注释
- **复用现有**——优先使用项目现有工具和模式

### 调试与问题解决
当开发遇到问题时，遵循以下流程（最多3次尝试）：
1. **记录问题**：
   - 记录具体操作步骤
   - 记录具体报错信息
   - 分析问题原因
2. **调研方案**：
   - 找到2-3个类似实现
   - 记录不同的解决思路
3. **重新评估**：
   - 抽象层级是否正确？
   - 能否拆成更小的问题？
   - 有没有更简单的实现？
