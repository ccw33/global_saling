# 五角色协作工作流

本文档说明产品经理、架构设计师、开发规划师、开发工程师、QA工程师的协作流程。

## 角色职责

| 角色 | 主要职责 | 交付物 |
|------|----------|--------|
| **产品经理** | 需求分析、用户价值定义、功能规划 | `REQUIREMENTS.md` |
| **架构设计师** | 技术选型、架构设计、技术决策 | `ARCHITECTURE.md` |
| **开发规划师** | Epic-Story拆分、开发计划制定 | `IMPLEMENT_PLAN.md` |
| **开发工程师** | 代码实现、单元测试、功能交付 | 功能代码、单元测试 |
| **QA工程师** | 测试策略、测试用例、质量保障 | `QA_TEST_PLAN.md`、测试报告 |

## 协作流程

### 阶段1：需求分析 (产品经理)
```
产品经理
  ↓
分析用户需求 → 定义业务价值 → 编写用户故事
  ↓
创建 REQUIREMENTS.md
  ↓
交付给架构设计师和开发规划师
```

**关键产出：**
- 清晰的业务背景和用户痛点
- 标准化的用户故事格式
- 明确的验收标准

### 阶段2：架构设计 (架构设计师)
```
架构设计师
  ↓
阅读 REQUIREMENTS.md → 评估技术可行性 → 选择技术栈
  ↓
设计系统架构 → 定义目录结构
  ↓
创建 ARCHITECTURE.md
  ↓
交付给开发规划师
```

**关键产出：**
- 技术框架选型和选择理由
- 清晰的目录结构规划
- 高层架构设计思路
- 技术约束和共同模式

### 阶段3：开发规划 (开发规划师)
```
开发规划师
  ↓
阅读 REQUIREMENTS.md 和 ARCHITECTURE.md
  ↓
识别 Epic → 拆分 Story → 定义验收标准
  ↓
制定实施计划 → 排定优先级
  ↓
创建 IMPLEMENT_PLAN.md
  ↓
交付给开发工程师
```

**关键产出：**
- Epic-Story结构化分解
- 每个Story的验收标准
- 开发阶段划分和时间安排
- DoD (Definition of Done)

### 阶段4：代码实现 (开发工程师)
```
开发工程师
  ↓
阅读 ARCHITECTURE.md 和 IMPLEMENT_PLAN.md
  ↓
理解架构 → 编写代码 → 编写测试
  ↓
自测 → 修复bug → 代码审查
  ↓
提交到测试环境
  ↓
通知QA工程师
```

**关键产出：**
- 高质量的代码实现
- 完整的单元测试覆盖
- 清晰的代码注释和文档

### 阶段5：测试验证 (QA工程师)
```
QA工程师
  ↓
阅读所有相关文档 → 设计测试用例
  ↓
执行测试 → 发现bug → 反馈给开发
  ↓
回归测试 → 验收确认
  ↓
生成测试报告
  ↓
交付给产品经理
```

**关键产出：**
- 完整的测试计划和用例
- 详细的bug报告
- 测试执行报告和质量评估

### 阶段6：验收发布 (产品经理)
```
产品经理
  ↓
UAT测试 → 确认功能符合预期
  ↓
与团队确认发布时间
  ↓
执行发布
```

## 文档组织结构

```
docs/feature/<feature>/
├── REQUIREMENTS.md      # 产品需求文档 (产品经理)
├── ARCHITECTURE.md      # 技术架构设计 (架构设计师)
├── IMPLEMENT_PLAN.md    # 开发实施计划 (开发规划师)
└── QA_TEST_PLAN.md      # QA测试计划 (QA工程师)
```

## 协作原则

### 1. 文档先行
- 所有重要决策都记录在文档中
- 文档是角色间协作的主要媒介
- 保持文档的及时更新

### 2. 明确交接
- 每个阶段完成后明确交付物
- 接收方确认理解后再开始工作
- 保持沟通渠道畅通

### 3. 质量门禁
- 每个阶段都有明确的完成标准
- 不达标不进入下一阶段
- 问题及时反馈和解决

### 4. 灵活调整
- 保持计划的灵活性
- 根据实际情况合理调整
- 变更需要沟通确认

## 常见协作场景

### 场景1：新功能开发
```
产品经理 → 需求分析
  ↓
架构设计师 → 技术架构
  ↓
开发规划师 → 实施计划
  ↓
开发工程师 → 代码实现
  ↓
QA工程师 → 测试验证
  ↓
产品经理 → 验收发布
```

### 场景2：Bug修复
```
QA工程师 → 提交bug报告
  ↓
开发工程师 → 分析修复
  ↓
QA工程师 → 回归测试
  ↓
产品经理 → 确认修复
```

### 场景3：技术重构
```
架构设计师 → 重构方案
  ↓
开发规划师 → 拆分任务
  ↓
开发工程师 → 执行重构
  ↓
QA工程师 → 回归测试
  ↓
产品经理 → 验收确认
```

## 角色间关键协作点

| 协作点 | 角色1 → 角色2 | 关键动作 |
|--------|--------------|----------|
| 需求澄清 | 产品经理 → 架构设计师 | 讨论技术可行性 |
| 需求确认 | 产品经理 → 开发规划师 | 确认用户故事 |
| 技术约束 | 架构设计师 → 开发规划师 | 传递架构要求 |
| 验收标准 | 开发规划师 → 开发工程师 | 明确交付标准 |
| 功能确认 | 开发工程师 → 产品经理 | 验证功能实现 |
| Bug反馈 | QA工程师 → 开发工程师 | 报告和跟进bug |
| 质量评估 | QA工程师 → 产品经理 | 提供测试报告 |
| 发布决策 | 产品经理 → 全体 | 确认发布时机 |

## 质量保障机制

### 1. 文档质量
- 需求文档清晰明确
- 架构文档简洁实用
- 实施计划可执行

### 2. 代码质量
- 遵循代码规范
- 完整的单元测试
- 代码审查通过

### 3. 测试质量
- 测试覆盖充分
- Bug报告详细
- 回归测试完整

### 4. 交付质量
- 功能符合需求
- 用户体验良好
- 系统稳定可靠

## 持续改进

### 1. 定期回顾
- 每个功能完成后回顾协作过程
- 总结成功经验和问题教训
- 持续优化协作流程

### 2. 知识积累
- 记录常见问题和解决方案
- 建立技术知识库
- 分享最佳实践

### 3. 工具优化
- 评估和引入更好的协作工具
- 自动化重复性工作
- 提升协作效率

## 注意事项

1. **角色边界清晰** - 每个角色专注于自己的职责，不过度干预
2. **沟通及时** - 问题及时沟通，避免信息不对称
3. **尊重专业** - 尊重每个角色的专业判断
4. **以价值为导向** - 所有工作都以业务价值为目标
5. **质量优先** - 不为了速度牺牲质量
6. **持续学习** - 持续学习和改进，提升协作效率
